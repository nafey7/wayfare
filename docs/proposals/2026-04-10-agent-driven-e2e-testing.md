# Agent-Driven Testing & Storybook Design System

> **Status:** Active
> **Date:** 2026-04-10
> **Last Updated:** 2026-04-11
> **Author:** Roel Sadza
> **Companion doc:** [2026-04-10-dx-and-testing-strategy.md](./2026-04-10-dx-and-testing-strategy.md) — high-level vision and roadmap. This doc is the hands-on implementation: config, YAML, commands.

## Summary

Introduce a two-layer AI agent-driven testing and design workflow:

1. **Storybook** (component layer) - fast design iteration, visual review, component documentation
2. **Playwright E2E** (application layer) - full user flows against the running app

Both integrate with Claude Code via MCP servers, giving the agent direct access to browse components (Storybook) and interact with the live app (Playwright). For Playwright specifically, both **MCP** and **`@playwright/cli`** are installed: MCP for agentic loops, CLI for token-efficient one-shots and persistent sessions.

## Testing Pyramid

| Layer | Tool | Speed | What It Catches | Feedback Loop |
|---|---|---|---|---|
| **Component** | Storybook + Claude visual review (`/screenshot`) | Seconds | Design regressions, prop issues, theme breakage, a11y | Instant (dev server) |
| **E2E** | Playwright agents | Minutes | Full user flows, API integration, auth, bookings | Docker (local) or staging (post-deploy) |

Storybook is the fast loop for UI changes. Playwright E2E is the confidence layer that the full app works.

## Part 1: Storybook Design System

### Why Storybook

- 175 component files across 12 feature modules in `frontend-v2/`
- Centralized MUI 7.1.0 theme with custom palette and typography
- Vite 6.0.4 (Storybook 10's default builder)
- No Figma in the workflow; Claude Code is the primary UI modifier

### `@storybook/addon-mcp`

Official first-party addon (v0.5.0) that runs an MCP server at `http://localhost:6006/mcp`. Gives Claude Code:

- **Component discovery**: list all components, read prop APIs, see usage examples
- **Story generation**: create stories from component metadata
- **Test execution**: run visual/interaction/accessibility tests
- **Preview**: render stories and verify changes

Configured in [.mcp.json](.mcp.json):

```json
{
  "storybook": {
    "type": "streamable-http",
    "url": "http://localhost:6006/mcp"
  }
}
```

### Visual Review: Claude Instead of Chromatic

No Chromatic needed. Claude Code is multimodal and can view screenshots directly:

1. Storybook renders stories
2. The `/screenshot` skill takes a screenshot via `playwright-cli` (named session `voya-storybook` so login state and config persist)
3. Claude views the screenshot file and reasons about the result

Advantages over pixel-diff:
- Understands intent ("padding changed because we added a label" vs "PIXEL MISMATCH")
- Won't flag anti-aliasing or subpixel rendering noise
- Free

For automated CI without Claude in the loop, Playwright's `toHaveScreenshot()` provides free baseline comparison.

### Storybook Preview Deployments (Cloudflare Pages)

Three deployment tiers via a single Cloudflare Pages project (`voya-storybook`):

| Deployment | Trigger | URL Pattern | Purpose |
|---|---|---|---|
| **PR preview** | PR opened/updated | `pr-{N}.voya-storybook.pages.dev` | Review design changes before merge |
| **Main** | Merge to main | `main.voya-storybook.pages.dev` | Current design system, always up to date |
| **Release** | Tag push (v*.*.*) | `v2026-4-3.voya-storybook.pages.dev` | Historical reference |

Free tier handles ~500 builds/month, more than enough.

**Access control**: Cloudflare Access policy with email OTP, wildcard `*@myvoya.ai` (excluding `roelsadza@gmail.com` and the plaintech.* contractor domain to keep contractor access scoped through Roel). This is set up at the Zero Trust account level, not in the deploy workflow.

CI workflow lives at [.github/workflows/deploy-storybook.yml](.github/workflows/deploy-storybook.yml). Sticky PR comment with the deployment URL is posted on every PR via the `marocchino/sticky-pull-request-comment` action.

### Storybook Setup (as shipped)

```bash
cd frontend-v2
npx storybook@latest init --type react --builder vite
npm install @storybook/addon-mcp
```

Configuration:
- `.storybook/preview.tsx`: MUI ThemeProvider + CssBaseline decorator + Redux Provider
- `.storybook/main.ts`: Vite builder, `@/` path alias matching `vite.config.ts`
- Production theme (`src/theme.ts`) used so Storybook matches staging exactly

Critical lesson from setup: there were two theme files (`src/theme.ts` for production with Lato/#BFC6F4, and `src/theme/index.ts` aspirational with Inter/#667eea). Vite resolves the `.ts` file before the directory's `index.ts`, so production was using `src/theme.ts`. Foundation stories caught this on day one. Tracked in [#707](https://github.com/myvoya/voya/issues/707).

## Part 2: Playwright E2E Testing

### Two-Tier Test Execution

| Environment | Trigger | Target | Auth | Mocks |
|---|---|---|---|---|
| **Local** | Developer / agent via docker compose | `localhost:8001` | MailHog (register on the fly) | FlightLogic mock |
| **Staging** | Post-deploy on main | `staging.myvoya.ai` | Dedicated test account ([#714](https://github.com/myvoya/voya/issues/714) — pending) | FlightLogic test env |

> **Note:** Docker E2E in CI (feature branch PRs) is deferred to Phase 5. The Docker stack (MongoDB, FlightLogic mock, backend build) adds ~5-10 min to CI. Staging post-deploy E2E is the primary confidence layer instead. See [#683](https://github.com/myvoya/voya/issues/683) for re-evaluation criteria.

### Browser Automation: MCP and CLI Both

Two complementary tools, both shipped:

**Playwright MCP** ([.mcp.json](.mcp.json)):
```json
{
  "playwright": {
    "command": "npx",
    "args": ["-y", "@playwright/mcp@0.0.70", "--caps", "testing"]
  }
}
```

Loads 32+ browser tools as schemas. Default snapshot mode uses the accessibility tree (2-5KB per snapshot, cheap and fast). Best for **multi-step agentic loops**: explore the app, react to what's on the page, generate tests, self-heal.

**`@playwright/cli`** (devDep in `testing/`, wrapper at [bin/playwright-cli](bin/playwright-cli)):
```bash
./bin/playwright-cli -s=voya-staging goto https://staging.myvoya.ai
./bin/playwright-cli -s=voya-staging screenshot --filename=screenshot.png
./bin/playwright-cli list  # show active named sessions
```

No tool schemas in context (token-efficient). Persistent named sessions keep cookies/auth across invocations. Best for **deterministic operations**: take a screenshot, get a cookie, smoke check a URL. Used by the `/screenshot` skill.

The Playwright team explicitly recommends CLI + SKILL for coding agents. Voya uses both, as recommended.

### Playwright Agent Pipeline

```
Planner   --> specs/*.md     (Markdown test plans)
Generator --> e2e/tests/    (JS test files, alongside hand-written)
Healer    --> fixes failing tests (selector drift, timing) [Phase 5]
```

Agents initialized with `npx playwright init-agents --loop=claude --prompts`. A seed test encodes Voya's conventions (POM, fixtures, constants, `IS_STAGING` guards, `@mock-required` tagging). Initialization tracked in [#686](https://github.com/myvoya/voya/issues/686).

### Multi-Environment Config

`testing/playwright.config.js` resolves `TEST_ENV`:

```
TEST_ENV=local    -> localhost:8001  (compose.test.yaml, default for CI)
TEST_ENV=staging  -> staging.myvoya.ai (post-deploy job)
TEST_ENV=dev      -> localhost:3002  (Vite dev server)
```

Staging skips global setup/teardown (no test database to manage), uses HTTPS, and disables MailHog service checks. Test tagging via `grepInvert`:
- `local` runs all except `@staging`
- `staging` runs all except `@mock-required`
- `dev` runs all except both (uses different ports than `compose.test.yaml`)

### Environment-Aware Fixtures

[testing/fixtures/auth-fixtures.js](testing/fixtures/auth-fixtures.js):

- **`registeredUser`**: throws on staging with a clear error pointing at `@mock-required`. Local: registers via API + MailHog activation.
- **`authenticatedUser`**: branches on `IS_STAGING`. Staging: logs in with `STAGING_TEST_USER_EMAIL` / `STAGING_TEST_USER_PASSWORD`. Local: registers + activates + sets password + logs in via the full flow.
- **`userWithResetToken`**: throws on staging (needs MailHog).

### Required Convention: `IS_STAGING` Guards

A pattern the PR #715 staging E2E rollout established as a hard requirement: **any test that touches MailHog, MongoDB directly, or other local-only services must guard those calls with `IS_STAGING`**.

```javascript
import { IS_STAGING } from '../utils/constants.js';

test.beforeEach(async ({ request }) => {
  // Initialize helpers (MailHog/DB only available on local; staging uses real services)
  if (!IS_STAGING) {
    mailhog = new MailHogHelper(request);
    dbHelper = new DatabaseHelper();
    await dbHelper.connect();
  }

  // API calls work in both environments
  const health = await request.get(URLS.BACKEND + URLS.HEALTH);
  expect(health.ok()).toBeTruthy();

  // Local-only cleanup
  if (!IS_STAGING) {
    await mailhog.clearEmails();
    await dbHelper.clearTestUsers();
  }
});
```

**Why:** `DatabaseHelper.connect()` has a 5s `serverSelectionTimeoutMS` and **rethrows** on failure. Without the guard, every `beforeEach` blocks for 5s and fails before any assertion runs, breaking entire test files in the staging E2E job. PR #715 caught this on the first staging E2E run and was fixed before merge.

If a whole test file relies on MailHog/MongoDB and can't reasonably guard, tag the file with `@mock-required` instead.

### Staging: Post-Deploy E2E (Primary Confidence Layer)

Post-deploy job in [.github/workflows/deploy-staging.yml](.github/workflows/deploy-staging.yml), shipped in PR #715:

```yaml
e2e-staging:
  name: E2E Smoke Tests (Staging)
  needs: [deploy, purge-cache]
  runs-on: ubuntu-latest
  permissions:
    contents: read

  steps:
    - uses: actions/checkout@v4

    - uses: actions/setup-node@v4
      with:
        node-version: 20
        cache: npm
        cache-dependency-path: testing/package-lock.json

    - name: Install dependencies
      working-directory: testing
      run: npm ci

    - name: Install Playwright browsers
      working-directory: testing
      run: npx playwright install chromium --with-deps

    - name: Run E2E tests against staging
      working-directory: testing
      env:
        TEST_ENV: staging
        STAGING_TEST_USER_EMAIL: ${{ secrets.STAGING_TEST_USER_EMAIL }}
        STAGING_TEST_USER_PASSWORD: ${{ secrets.STAGING_TEST_USER_PASSWORD }}
      run: npx playwright test

    - name: Upload Playwright report
      if: always()
      uses: actions/upload-artifact@v4
      with:
        name: staging-e2e-report
        path: testing/playwright-report/
        retention-days: 7
```

Uses staging test account credentials from GitHub secrets (when [#714](https://github.com/myvoya/voya/issues/714) lands). Tests requiring MailHog or mock APIs are tagged `@mock-required` and skipped automatically via `grepInvert`.

The `notify` job downstream of `e2e-staging` uses `if: always()` so a test failure does not block the deploy summary.

### CI: E2E on Feature Branches (Deferred - Phase 5)

### Test Tagging Strategy

```javascript
// Tests that need mocks (skip on staging)
test('booking with mock FlightLogic', { tag: '@mock-required' }, async () => { ... });

// Tests that work everywhere
test('user can log in', async () => { ... });

// Staging-only tests (real API validation)
test('health check returns 200', { tag: '@staging' }, async () => { ... });
```

**Examples of `@mock-required` in the current suite (post PR #715):**
- `e2e/tests/auth/registration.spec.js`, `e2e/tests/auth/login.spec.js` — full UI registration with MailHog activation
- `e2e/tests/flights/*.spec.js` (most) — booking with mock FlightLogic
- `e2e/tests/hotels/booking-flow.spec.js` — booking with mock FlightLogic
- `api/auth.spec.js` Flow B test — uses `mailhog.waitForEmail` directly
- `api/auth.spec.js` Password Reset tests that register synthetic users — would pollute staging DB and trigger real SendGrid sends to bogus addresses
- `api/email-payment-*.spec.js`, `api/payment-security.spec.js` — email content tests

## Combined Developer Workflow

```
Claude Code modifies a component:
  1. Storybook MCP: check existing component API, generate/update story
  2. Storybook dev server: instant visual feedback
  3. /screenshot skill: take a screenshot via playwright-cli + voya-storybook session
  4. Claude views the screenshot, reasons about the result

PR created:
  5. CI runs lint, type-check, unit tests
  6. Coverage sticky PR comment posted
  7. CI builds Storybook → deploys to pr-{N}.voya-storybook.pages.dev
  8. Cloudflare Access OTP gates the preview URL to *@myvoya.ai
  9. Team reviews Storybook preview for design changes
 10. Claude auto-review posts inline + summary review

Merge to main:
 11. Deploy to staging
 12. Post-deploy Playwright E2E against staging.myvoya.ai
 13. E2E report uploaded as artifact

Tag for release:
 14. Deploy to production
 15. Storybook deployed at v{version}.voya-storybook.pages.dev
```

## Decisions

| Decision | Choice | Rationale |
|---|---|---|
| Visual regression tool | Claude + Playwright screenshots (no Chromatic) | Free, intent-aware, Claude is already the modifier |
| Storybook previews | Cloudflare Pages per-PR | Already using Cloudflare, automatic cleanup, free |
| Storybook preview access | Cloudflare Access OTP, `*@myvoya.ai` wildcard | Free, no SSO setup needed, scoped to team domain |
| E2E on feature branches | Local only (compose.test.yaml), not in CI | Docker stack too heavy for CI (~5-10 min) |
| E2E confidence layer | Post-deploy on staging | Real environment, catches integration issues after merge |
| Docker E2E in CI | Deferred to Phase 5 ([#683](https://github.com/myvoya/voya/issues/683)) | Re-evaluate after staging E2E proven |
| **Browser automation** | **Playwright MCP _and_ `@playwright/cli` (both)** | **MCP for agentic loops, CLI for token-efficient one-shots and persistent sessions** |
| **Local-only services in tests** | **`IS_STAGING` guards in `beforeEach`, or `@mock-required` tag for whole-file mocks** | **Without the guard, `dbHelper.connect()` blocks staging E2E for 5s and fails before any assertion (PR #715)** |
| Agent-generated test location | Alongside hand-written in `e2e/tests/` | Single test suite, shared fixtures |
| Staging auth | Dedicated test account ([#714](https://github.com/myvoya/voya/issues/714)) | No MailHog on staging, stable credentials |
| Stale tests | Retire, let agents regenerate | 64% failure rate, manual fixes not worth it |
| `@playwright/cli` version pinning | Pin exact (`0.1.6`, no caret) | Pre-1.0 semver; `^` accepts any `0.x.y`; PR #718 review feedback |
